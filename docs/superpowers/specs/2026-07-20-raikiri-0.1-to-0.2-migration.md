# raikiri 0.1 → 0.2 migration guide (Sprint 9-10 hardening security batch)

## 0. この文書の位置付け

raikiri workspace の Sprint 9 (hardening/1) と Sprint 10 (hardening/2) で
消化した SEC HIGH 系 fix のうち、**public API surface に破壊的変更として
現れる 2 領域** を fulgur (raikiri の primary external consumer) 向けに
1 か所に集約した migration guide。

- **q3f (raikiri-style Arc/SmolStr shape)** — Sprint 9 で landed、Sprint 10
  で wall/umbrella formal declare。
- **4kw (`raikiri::parse_html_with_limits` + `RenderLimits::max_input_bytes`)** —
  Sprint 9 に hard-coded const で stopgap、Sprint 10 で wall/traits Option A
  promotion で正規形卒業。

いずれも「security fix の副作用として API surface が動いた」もの — SEC
finding そのものと切り分けて、consumer 側でどこを触れば upgrade できるかを
最短パスで示す。

**live impact 現状**: Sprint 10 時点で raikiri-spike workspace の **consumer
crate 群** (`raikiri-dom` / `raikiri-paint` / `raikiri` / `raikiri-html` /
`raikiri-vrt`) 内に該当 constructor 呼び出し **0 件** (merge 時 grep 検証済、
bd raikiri-spike-q3f "Investigation" section)。owner の `raikiri-style` 内は
test fixture が `ContentComponent::Literal(SmolStr::new(..))` 等を使うが、
これは shape 変更に追従済で consumer migration の対象外。raikiri-spike 外の
consumer (fulgur) は未検証だが、workspace 内 empty の precedent が強い。本
doc は fulgur 側 upgrade 時の対照表として使う。

## 1. raikiri-style — `PropertyValue::Content` / `StringSet` / `ContentComponent::Literal`

### 1.1 何が変わったか

Sprint 9 hardening (bd raikiri-spike-d9y.1、SEC HIGH cascade memory DoS
fix) が **cascade winner clone** と **inheritance walk stack entry clone** を
`Arc` bump に落とすため、以下 3 変更を landed:

| 対象 | 0.1 (pre-d9y.1) | 0.2 (post-d9y.1) |
| --- | --- | --- |
| `PropertyValue::Content` payload | `Vec<ContentComponent>` | `Arc<Vec<ContentComponent>>` |
| `PropertyValue::StringSet` payload | `Vec<(SmolStr, Vec<ContentComponent>)>` | `Arc<Vec<(SmolStr, Vec<ContentComponent>)>>` |
| `ContentComponent::Literal` payload | `String` | `SmolStr` |

Sprint 9 Wave 2 (bd raikiri-spike-d9y.2、同 SEC HIGH の counter-* 拡張) で
同 pattern を適用:

| 対象 | 0.1 | 0.2 |
| --- | --- | --- |
| `PropertyValue::CounterReset` payload | `Vec<(SmolStr, i32)>` | `Arc<Vec<(SmolStr, i32)>>` |
| `PropertyValue::CounterIncrement` payload | 同上 | 同上 |
| `PropertyValue::CounterSet` payload | 同上 | 同上 |

**なぜ `#[non_exhaustive]` が防いでくれないか**: `PropertyValue` / `ContentComponent`
両方に enum-level `#[non_exhaustive]` は 0.1 時点から付いていた。この attribute は
「downstream の `match` に `_ =>` arm を強制することで新 variant 追加を
forward-compatible にする」ものだが、**既存 variant の tuple constructor
呼び出しは block しない**。ゆえに existing variant の payload **type** 変更は
downstream constructor で普通に compile-break する (bd raikiri-spike-d9y.1
codex final review 非軽微 finding、q3f 起票理由)。

### 1.2 Read-side migration (通常は何もしない)

Pattern-match で payload を読むだけの consumer は **書き換え不要**:

- `Arc<Vec<T>>` は `Deref<Target = Vec<T>>` → `Deref<Target = [T]>` を chain
  で提供するため、`match pv { PropertyValue::Content(components) =>
  components.iter().for_each(..) }` のような使い方が透過的に継続動作
  する (`&Arc<Vec<T>>` は autoderef 経由で `&[T]` として渡せる)。
- `SmolStr` は `Deref<Target = str>` を提供するため、`match cc {
  ContentComponent::Literal(s) => &*s }` / `s.as_str()` / `s.len()` /
  `for c in s.chars()` などの `&str` API がそのまま動作する。

### 1.3 Construct-side migration (write する consumer のみ)

Payload を **construct** する consumer は以下 3 種類の書き換え:

**PropertyValue::Content**:

```
// 0.1
PropertyValue::Content(vec![
    ContentComponent::Literal(String::from("Chapter ")),
])

// 0.2
PropertyValue::Content(Arc::new(vec![
    ContentComponent::Literal(SmolStr::new("Chapter ")),
]))
```

**PropertyValue::StringSet** (outer `Vec` のみ Arc 化、inner は 0.1 のまま):

```
// 0.1
PropertyValue::StringSet(vec![
    (SmolStr::new("name"), vec![ContentComponent::Literal(String::from("x"))]),
])

// 0.2
PropertyValue::StringSet(Arc::new(vec![
    (SmolStr::new("name"), vec![ContentComponent::Literal(SmolStr::new("x"))]),
]))
```

**ContentComponent::Literal** (`String` → `SmolStr`):

- Owned `String` から: `ContentComponent::Literal(SmolStr::from(owned_string))`
- 静的 `&str` から: `ContentComponent::Literal(SmolStr::new("literal"))`

`SmolStr::new(..)` は `AsRef<str>` を受けるので `&str` / `&String` / `String`
いずれも渡せる。23 bytes 以下は heap allocation なし (inline、`smol_str`
0.3.6 `INLINE_CAP = InlineSize::_V23`)、超過分は内部 `Arc<str>` 保存で
clone O(1)。

### 1.4 CounterReset / CounterIncrement / CounterSet

同 pattern:

```
// 0.1
PropertyValue::CounterReset(vec![(SmolStr::new("c1"), 0)])

// 0.2
PropertyValue::CounterReset(Arc::new(vec![(SmolStr::new("c1"), 0)]))
```

`Vec<(SmolStr, i32)>` の inner tuple は 0.1 と同じ shape。

### 1.5 Rationale (為念)

- **DoS 攻撃 shape**: `* { content: "<large string>" }` × N element、または
  parent 大 content × N child。0.1 は cascade winner clone + inheritance
  walk stack entry clone + per-node write で **O(N × M) memory blow-up** を
  起こしていた (M = content 長 / entry 数、N = element 数)。
- **Fix**: `Arc<Vec<..>>` wrap で clone を **shallow (Arc bump only)** に、
  `OnceLock` 保持の shared empty slot で per-node empty allocation regression
  も回避 (`empty_content_list()` / `empty_string_set_entries()` /
  `empty_counter_entries()`)。詳細は `crates/raikiri-style/src/property.rs`
  の各 helper の docstring。

## 2. raikiri (umbrella) — `parse_html_with_limits` + `RenderLimits::max_input_bytes` + `LimitKind::InputBytes`

### 2.1 何が変わったか

Sprint 9 Wave 3 (bd raikiri-spike-d9y.3、SEC HIGH `parse_html` unbounded-read
DoS fix) は **Option B stopgap** で hard-coded 32 MiB const + 既存
`LimitKind::AggregateBytes` re-use により umbrella crate 内 autonomous 完結。

Sprint 10 で wall/traits crossing の **Option A promotion** (bd raikiri-spike-4kw、
sve decision) が完了し、正規形卒業:

| 対象 | 0.1 (pre-Sprint 9) | 0.1.x (Sprint 9 stopgap) | 0.2 (Sprint 10 Option A) |
| --- | --- | --- | --- |
| `raikiri::parse_html` | unbounded read | 32 MiB hard-coded cap | 32 MiB default via `RenderLimits::default()` |
| `raikiri::parse_html_with_limits` | 存在せず | 存在 (Option B stopgap) | `RenderLimits::max_input_bytes` を consult |
| `raikiri_traits::RenderLimits::max_input_bytes` | 存在せず | 存在せず (stopgap 内 const) | `Option<u64>`, default `Some(32 * 1024 * 1024)` |
| `raikiri_traits::LimitKind` | `Pages` / `DomNodes` / `TargetSlots` / `LayoutBufferEntries` / `AggregateBytes` | `AggregateBytes` を stopgap で流用 | `InputBytes` variant 追加 |

### 2.2 Default consumer は書き換え不要 (fail-closed 継承)

`parse_html(input, &opts)` を呼び出し `RenderLimits::default()` に依存する
consumer は behavior 不変:

- default `max_input_bytes` = `Some(32 * 1024 * 1024)` は Wave 3 stopgap の
  hard-coded 値と一致 (bd raikiri-spike-4kw close reason)。
- `parse_html` 自体が内部で `parse_html_with_limits(input, opts,
  RenderLimits::default())` を呼び出す thin wrapper (bd raikiri-spike-4kw
  landed 契約、`crates/raikiri/src/parse.rs`)。
- したがって「default cap は必ず enforce される」 fail-closed 原則が保たれる。

### 2.3 Cap を調整したい consumer

**Fluent builder** (推奨):

```
use raikiri::{RenderLimits, RenderLimitsBuilder, parse_html_with_limits, ParseOptions};

let limits = RenderLimits::builder()
    .max_input_bytes(Some(16 * 1024 * 1024)) // 16 MiB に絞る
    .build();
let doc = parse_html_with_limits(input, &opts, limits)?;
```

**Field への直接代入は不可** — `RenderLimits` は `#[non_exhaustive]` が
付与されているため、Rust Reference の規定 (`Non-exhaustive types cannot be
constructed outside of the defining crate`) により **downstream crate から
`RenderLimits { .. }` struct expression (functional update syntax
`..RenderLimits::default()` を含む) は compile error**。field 単位で
override したい場合も上記 fluent builder を使う。builder に該当 method が
未提供の field は upstream に追加要請 (bd 起票) するか、`RenderLimits::default()`
を base に build する。

### 2.4 Cap を **無効化** したい consumer (SEC 上の含意あり)

```
let limits = RenderLimits::builder()
    .max_input_bytes(None)   // ← unbounded read
    .build();
```

**Security note (verbatim、`crates/raikiri-traits/src/config.rs` field doc
より)**:

> `None` は cap を無効化し、SEC-HIGH d9y.3 で close した `parse_html`
> unbounded-read DoS を **再暴露する** (attacker が任意サイズの HTML を
> 送り込み OOM を誘発可能)。明示的な opt-out としてのみ使用し、default
> (`Some(32 MiB)`) から離れる場合は upstream で別途 bound を設ける前提で
> あること。

### 2.5 `LimitKind::InputBytes` の追加 (error handling side)

`RenderError::LimitExceeded { kind, .. }` に対する `match` を書いている
consumer は、`LimitKind` に `InputBytes` variant が追加された点に注意。
`LimitKind` は 0.1 時点から `#[non_exhaustive]` なので `_ =>` arm を持つ
downstream `match` は **compile 継続する**。ただし parse-time DoS を
狙って撃つ attacker input と post-parse memory blow-up は要因が異なるため、
明示的に区別したい場合は arm を追加する:

```
// 0.1
match err {
    RenderError::LimitExceeded { kind: LimitKind::AggregateBytes, .. } => "memory",
    _ => "other",
}

// 0.2 (推奨: parse-time input cap を分けて log/metric)
match err {
    RenderError::LimitExceeded { kind: LimitKind::AggregateBytes, .. } => "post-parse memory",
    RenderError::LimitExceeded { kind: LimitKind::InputBytes, .. } => "parse-time input cap",
    _ => "other",
}
```

**Semantic 分離** (verbatim、`crates/raikiri-traits/src/error.rs` variant doc
より):

> `InputBytes` は **parse-time** の raw input byte stream を pin する
> fail-closed 早期返却用 (`parse_html_with_limits` が read 段階で enforce)。
> `AggregateBytes` は **post-parse** の approximate memory footprint。ゆえに
> attacker が巨大 HTML を送りつけて OOM を誘発する DoS 対策としては
> `InputBytes` の方が直接的。

### 2.6 削除 / rename された symbol

- Sprint 10 gate §8.2 sibling-convention drop (bd raikiri-spike-10i audit
  trail): `RenderLimitsBuilder::with_max_input_bytes(..)` は **存在しない**
  (他 field の builder method が `max_document_pages` / `max_dom_nodes` / ...
  と prefix なしの sibling convention に揃っているため)。設定 method 名は
  `max_input_bytes(Option<u64>)` 一本。
- Sprint 9 Wave 3 の internal `INPUT_BYTES_CAP: u64` const は `raikiri::parse`
  module から削除 (Option A promotion で `limits.max_input_bytes` に data-flow
  が移った)。この const は元々 pub でなかったので consumer には影響しない。
