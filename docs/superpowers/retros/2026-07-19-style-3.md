### S2. m4.1 planner 9y9(a) miss — Verification-prose vs concrete-rank contradiction inside a single bullet

`m4.1` bd description Verification #2 read: *"`!important` 反転: Author !important > UA !important > Author normal > UA normal (css-cascade-4 §6.2)"*.

The prose ordering `Author !important > UA !important` **is a spec violation** — CSS Cascading L4 §6.2 states User Agent !important is the strongest origin (UA-important > User-important > Author-important > Author > User > UA — reversed at the !important boundary). The parenthetical *within the same bullet* `(UA_imp=3 > Author_imp=2)` is spec-compliant, and the implementation + tests + commit body + bd close-reason all match spec (test `cascade_page_important_ua_beats_important_author` passes).

The gap: planner discipline 9y9(a) *"Task-authoring primary-source verification"* was applied to the Spec anchors section (URLs verified via WebFetch, correct anchor `#cascade-origin` cited) but not to the discrete **claim** in Verification #2's prose. The claim was authored from memory / natural-language ordering intuition, not from a re-read of the spec's Important-priority table.

Compounding: within the same Verification #2 bullet, the prose ordering and the parenthetical rank numbers **contradict each other**. Even without spec verification, an internal-consistency read would have caught the divergence.

Two related-but-distinct planner discipline gaps:

- **(i) Per-claim primary-source verification, not just anchor URL**: 9y9(a) currently requires spec verification of "task description の Verification 項目に … 特定挙動を書く場合"; the current firing pattern verifies anchor URLs but does not verify each discrete concrete claim (rank orderings, priority tables, edge-case behaviors) within a bulleted verification list.
- **(ii) Within-bullet internal consistency**: when a single Verification bullet contains both a prose narrative and a concrete numeric/tabular claim, the two should reconcile before dispatch. This is a stronger check than 37n's sibling-convention scan (37n is inter-file, this is intra-bullet).

n=1 for this specific failure mode. Filed as **decision D1** (proposed extension of 9y9(a)). Human approver may fold both (i) and (ii) into 9y9(a) as a "per-claim + internal-consistency" refinement, or accept only (ii) as a lighter internal-consistency requirement, or defer for more evidence.

Positive datapoint against catastrophe: **the implementation, tests, commit body, and bd close-reason are all spec-compliant** — the failure was contained at the planner-authoring layer and did not propagate downstream. reviewer:spec's evaluating-side read (per 9y9(c)) also caught it independently via bd comment self-note. This is exactly the "surfaced-by-discipline failure" mode Sprint 5 Observation D noted: hard checks worked, so a soft failure had room to surface for retro capture.
