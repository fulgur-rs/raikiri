## Signals (5)

### S1. First decompose event in scope/style — bd task description embedded a spec error

`rbo`'s bd task description Verification list item 2 required `:nth-page(An+B)` parsing. css-engine implemented it faithfully as "task-directed scaffolding extension". reviewer-spec Finding 1 (§8.2) then verified against CSS Paged Media L3 §3.2 (WebFetch) and L4 Editor's Draft — `:nth-page` is NOT in either spec (L4 only forward-states "future versions may add other pseudo-classes"). This is the exact fail-closed case in `autonomy.md` 原則 3.

Coordinator decompose (`848b37c`) removed the variant + tests + doc reference. `blocked/human` child `raikiri-spike-64s` filed with 3 option rubric (drop / feature-flag / raikiri-local extension) for user's spec-scope call. Merge of the trimmed rbo branch proceeded independently and passed §8.3 in 2 iters.

Root cause: the task description was authored (by a prior session, pre-dispatch) with `:nth-page` treated as a natural extension of the L3 page pseudo family, but no primary-source verification was performed at task-authoring time. reviewer-spec caught it at review time; this is the correct place for the check but a costly place (already-implemented code has to be stripped).

**Rule-improvement scope**: reviewer-spec's remit implicitly includes "verify the diff against spec"; consider explicitly widening to "verify the task's own spec claims (scope items, verification list) against primary source before or during code review". Companion to F4 citation discipline (see S3) — both are spec-citation hygiene. Filed as decision-candidate D2 below (bundled with F4 per advisor guidance).

### S2. Codex §8.3 F1 HIGH — stale-base race during review (adjacent to coord D1 / bd 9ce)

While rbo was in §8.3 codex review, the coord scope's `94e` Phase B landed on main as `268f36b`. Codex flagged this as F1 HIGH (stale-base concern in the review's evidence chain: the review had been reasoning against a base that was no longer main HEAD). The rbo branch and `94e` were file-level orthogonal (rbo: `raikiri-style/src/{page,ruletree,lib}.rs` new; 94e: raikiri-style `Cargo.toml` + `error.rs` reorganization + raikiri-dom trait impls), so `git rebase main` replayed cleanly with zero conflict, and iter 2 codex pass returned 0 new findings.

This is the **third** documented instance of "parallel scope sessions on shared main → base-staleness" (see Cross-scope observation section):
1. xno merge `6367bc2` — rebased over 3ps Phase A `d481a0f` (same session, sequential — commit body documents "3ps landing 検知 → git rebase main で d481a0f 上に replay").
2. coord `94e` sprint 2 S1 — session-style landed s85 `38f890e` between coord's §8.1.2 check and coord's `git merge --no-ff`. Filed as decision `raikiri-spike-9ce` (D1 in coord's retro): amend §8.1.2 with mandatory post-merge §8.1 re-run.

Note carefully: instance (2) is the **check→merge** flavor (coord D1 addresses it); instance (3) is the **review→merge** flavor (base becomes stale during multi-iter codex review). These are related but distinct — coord's D1 (post-merge §8.1 re-run) does not address the review-time stale-base case, because the review has already completed by then.

### S3. Codex §8.3 F4 LOW — numeric section citation drift across TR revisions

Codex F4 (rbo iter 1) flagged that two reviewer outputs (reviewer-spec finding text + codex own review text) cited different numeric section numbers for the same spec URL (CSS Paged Media L3 §3 vs §3.2). Both citations were true at the time of authoring but referenced different TR snapshots — the W3C editors' TR revisions renumber sections without moving the anchor fragments, so numeric citations decay.

Fix landed as `62dbb41` (F4 iter 1) + `11aaec2` (F4 iter 2 remove-final-numeric): keep the URL anchor fragment (`#page-selectors-syntax`) and section title, drop the numeric section identifier from doc comments.

**Rule-improvement scope**: reviewer-spec citation discipline. When citing CSS/HTML/DOM spec sections in code doc comments, task descriptions, or review outputs, prefer `URL#anchor-fragment + section title` over `§N.M` numeric identifier. Filed as decision-candidate D2 below (bundled with S1's task-authoring spec-verification concern).

### S4. Positive discipline — advisor call caught escalation misread

When rbo's reviewer-spec Finding 1 landed, coordinator's first read of the finding was that it was a doc issue (bd task description had wrong spec citation, fixable by editing the task description). Advisor was consulted and identified that F1 was a **behavioral divergence** (the shipped code implemented parsing for a variant that is not in the spec), which is a fail-closed case per `autonomy.md` 原則 3 — the fix is not "edit the doc" but "decompose the task and defer the variant to human ledger".

The advisor call cost seconds and prevented a mis-directed merge attempt that would have shipped spec-divergent behavior under coord's autonomous authority. This is the exact use case advisor exists for (`advisor before judgment call on escalation`).

**No rule change needed** — advisor call before consequential escalation judgment is already the norm per `raikiri-workflow` advisor tool documentation. This is recorded as a **positive discipline datapoint**, not a rule-improvement signal.
