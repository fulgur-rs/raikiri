## Signals (4)

### S1. §8.1.2 check-vs-merge timing gap — parallel scope session landed between my check and my `git merge`

During 94e's merge flow:
1. I ran §8.1.2 (main-state guard) against main HEAD `6367bc2` — clean.
2. Session-style landed `s85` as `38f890e` between my §8.1.2 check and my `git merge --no-ff worktree-94e-traits-decouple` command.
3. My local main advanced (shared git dir across worktrees) so the actual merge was a clean 3-way onto `38f890e` — auto-merged `cascade.rs` cleanly, all tests green post-merge.

No harm done in this instance because `s85` was itself gate-clean (its own §8.1.2 had passed). But the rule text in `gate.md §8.1.2` says:

> "main state は check の瞬間で snap、merge 直後に他 session が landing しても本 task の merge には影響しない"

My case was the **inverse**: another session landed AFTER my check but BEFORE my merge. The rule implicitly assumes check → merge are "atomic-ish" in wall-clock time, but with parallel scope sessions active this is no longer true.

**Cost of leaving gap**: if another session lands with drift on main between check and merge, the merge silently absorbs it into the merged state. Task's own §8.1 passing pre-merge does not detect this — the drift comes from the OTHER task's post-check landing.

**Mitigation candidates** (for decision-candidate below):
- Post-merge §8.1 re-run as a **mandatory** step after `git merge --no-ff` (already my ad-hoc practice this time, but rule text does not require it)
- Or: §8.1.2 check re-run immediately before `git merge` when another scope session has landed (detectable via `git log main..prev-main`)
- Or: accept the residual risk (small window, parallel session landings are themselves gate-clean by construction), and codify **only the post-merge re-run** as belt-and-suspenders

### S2. Advisor's grep-hole catch (hyphen vs underscore invariant)

During 94e dispatch, `advisor()` flagged that the "definitive invariant" grep in the task description — `grep -rn 'raikiri_traits' crates/raikiri-style/` (underscore form, matches Rust source `use raikiri_traits::...;`) — CANNOT match the Cargo.toml line `raikiri-traits = { workspace = true }` (hyphen form). The task description would silently pass its own completion check while leaving the Cargo.toml dependency in place.

This is a general lesson: **cross-crate refactor tasks that name a "definitive invariant grep" have a false-pass hole when the token exists in both language-side (`_`) and manifest-side (`-`) forms**. Both forms must be greped for a real completion signal.

I caught it before merge and verified both forms return zero. But the risk lives in every future cross-crate rename / dep-drop task.

**Rule-improvement scope**: `.claude/rules/agent-map.md` (dom agent + coord planner) or a fresh rule note. Low cost: one-line "when writing invariant greps for cross-crate refactor, cover both `snake_case` (source) and `kebab-case` (Cargo.toml)".
